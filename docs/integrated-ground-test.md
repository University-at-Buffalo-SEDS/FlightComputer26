# Integrated ground test image

The full design is in GroundStation26 `docs/integrated-ground-test.md`. This
page covers what lives in the FC.

## Build

The ground-test code is compiled only into a dedicated image. Build it with:

```sh
python3 build.py build --release --ground-test
```

This passes `-DINTEGRATED_GROUND_TEST=ON`, which defines `FC_GROUND_TEST=1`.
Every other build passes OFF explicitly. A flight image contains none of the
replay code: each hook in the sources sits under `#if FC_GROUND_TEST`, and
`tests/test_ground_test.py` checks this. The flight image reports no
ground-test support, so the station refuses the IGT commands.

Sizes, Release, measured against SEDSnet 6.0.3 (main ebdb444):

| Image | FLASH | Free | RAM |
| --- | --- | --- | --- |
| flight (default) | 467,064 B (+404 B vs dev e615de3) | 7,560 B | +0 B |
| `--ground-test` | 473,152 B (−128 B vs the previous ground-test build) | 1,472 B | 198,912 B |

Since then the SEDS-SD format block (+648 B flight, +652 B ground test) and
the flight-only SD read service (+3,400 B) were added: flight 471,192 B
(3,432 B free), `--ground-test` 473,892 B (732 B free). The ground-test image
has no network SD read service (CMake `FC_SD_SERVICE` is forced off there);
copy its card by hand.

The flight image's +404 B covers:

- the `SIM_SAMPLE` and `LAUNCH_SITE` schema entries;
- the station-set launch site (its handler and echo);
- the SD state and `FcSdRetry`;
- the compat command slots and one SD event label.

The ground-test image dropped the real-motion override, and reports CSV
problems as a reason code instead of text.

## Pieces

| File | Role |
| --- | --- |
| `Core/Src/ground_test.c`, `Core/Inc/ground_test.h` | Mode, CSV validation and parsing, rings, interpolation, gate state |
| `Core/Src/sdpipeline.c` | Calls `igt_sd_service()`: the SD task owns every IGT FileX call |
| `Core/Src/dma.c` | Replaces fresh IMU/baro samples while the replay runs; the real raw rows still go to SD |
| `Core/Src/distribution.c` | Replayed GPS and the rail swap; `SIM_SAMPLE` for replayed IMU/baro; real values on the normal types |
| `Core/Src/evaluation.c` | `SIM_SAMPLE` for estimator outputs during the replay; Landed ends it |
| `Core/Src/recovery.c` | `IGT_Enter`, `IGT_Live_Pyro`, `IGT_Dry_Run`, `IGT_Exit` (compat 29–32); replay start at Launch acceptance |
| `Core/Src/deployment_pulse.c` | Dry-run gate; every Stop/reset path calls `igt_stop()` |
| `Core/Src/fc_watchdog_recovery.c` | No checkpoint while the mode is on, so a reset cannot resume a replayed flight |
| `Core/Src/board_health.c` | BOARD_HEALTH word 14 bits 4..15 (bit 7: this is the ground-test image, sent from boot); word 6 bits 30..31: SD not ready / retry pending (both images) |
| `Core/Src/distribution.c` (`update_launch_site`) | `LAUNCH_SITE`: the station sets the GPS acceptance centre on the pad and the FC echoes it (both images) |
| `FileX/App/app_filex.c`, `Core/Src/sdpipeline.c` | A failed mount waits for `FcSdRetry` (compat 33) instead of spinning; SD state bits |

## SD card

The CSVs go in `/IGT/` (for example `IMU0.CSV`, `BARO0.CSV`, `GPS0.CSV`). The
schema is in the GS doc, section 4. To generate or convert the files, use
GroundStation26 `tools/igt_csv.py`.
Ready-made mock flights (a 6 in, 15 ft vehicle to 10,000 ft, plus stress
variants) are in GroundStation26 `test-data/igt/`, generated by
`tools/flight_profile/generate.py`.

## Host replay through the estimator

`tools/igt_replay_host.py <folder>` replays a CSV set through the real
`ground_test.c` validation and interpolation, `kalman.c` and `evaluation.c`
on the host (gcc -m32, ThreadX/HAL calls stubbed, deployments to a dry-run
stub). It prints the flight states the FC would reach, the drogue and main
decisions with the estimated altitude, and the estimator's apogee and peak
velocity. `--trace` writes the estimate every cycle. Use it to check a new
CSV set or an estimator change before a ground test:

```sh
python3 tools/igt_replay_host.py ../GroundStation26/test-data/igt/nominal_10k --trace /tmp/trace.csv
```

It runs the evaluator on the board's schedule (a baro conversion every 40 ms
from `Baro_ODR_25` in `recovery.c`, the ascent predict on the IMU just after
it, `tx_thread_sleep()` honoured),
but it does not model CPU time, sensor faults or telemetry. Those need the
native SITL (`igt_flow`, FirmwareSimulator) or the board.
